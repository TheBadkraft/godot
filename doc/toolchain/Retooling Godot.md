# Retooling Godot: Engine/Editor Split, Anvil & VS Code

Oct 16, 2026 · @David

## Overview and goals

This project uses Anvil as the single format for every configuration and scene file in Godot, with VS Code, the Godot editor and Blender each doing the job it does best, joined by Anvil as the common language.

**Point A (today):** the Godot editor is the primary tool. Scenes are built in it; VS Code is only set as the external editor for C# scripts.

**Point Z (destination):** VS Code is the authoring environment for everything — scenes and scripts alike — in whatever language a developer prefers, since Anvil's bindings already reach .NET, Python, Rust, C++, Java, Node, and WASM. No language is locked out; the goal is maximum inclusion of language choice. Godot itself shrinks to just its engine and renderer, reached through a stripped-down viewer/player rather than the full editor: author in VS Code, then run the result through the viewer to see it, test it, and confirm things like key bindings behave correctly. It is a testing apparatus, not an editor.

The path from A to Z is not fully known yet, and that is said plainly rather than papered over. Some waypoints are already identified below (the work plan, the Godot patch scope, the VS Code extension build-out). Others are not — there will be points in between that only become visible once earlier ones are reached. This doc is updated as those come into view, rather than pretending the full path is already mapped.

## Toolchain boundaries

The path to Point Z needs a hard line drawn down the middle of the toolchain: what stays permanently Godot's, and what VS Code takes over entirely.

**Godot stays sovereign over its engine and rendering.** Nothing here is replaced, forked, or reimplemented. Everything still runs through the Godot pipeline at runtime. This core stays stable and keeps growing on its own as upstream Godot development continues — this project is not a fork of the engine or the renderer.

**VS Code, through extensions, takes over authoring — completely.** That is scripting in any language, building out nodes, composing scenes, and eventually assembling an entire solution into a playable game, all without the Godot editor UI. This is the territory that grows over time as the VS Code extension build-out proceeds.

This split is as much organizational as technical. It lets Godot-core contributors keep doing upstream engine and rendering work undisturbed, while a separate community — VS Code extension developers and Anvil-binding maintainers — builds the authoring layer on top, each in whatever language they prefer. Real separation of concerns, on both the code and the people side.

- Patch the Godot source with the native C Anvil parser so Anvil replaces Godot's INI-style config and scene files.
- Consolidate all configuration under Anvil: scenes, project settings and Godot's own configuration.
- Keep each tool in its lane (VS Code for scripts and config, Godot for scene composition and runtime, Blender for 3D art) and build integration between them so nothing is lost moving from one to another.
- Once the Anvil script and extensible DSL work, replace Godot's scripting itself.
- Chip away at Godot's editor functionality through VS Code extensions over time, keeping Godot's engine as the backend.
- VS Code becomes the build trigger too, not just the authoring surface: a single entry point (`gd-build` wrapping the native SCons build, see below) replaces today's editor-hosted `GodotTools.BuildManager`, so compiling the project is something VS Code drives rather than something the Godot editor does on scripts' behalf.

## Work plan

Items 1 and 2 are the current focus. After they land, the list is reprioritized, mixing the lowest-hanging fruit in with the harder items.

**New lead-off item, ahead of the list below:** physically separate the Godot engine from the Godot editor in the repository itself — a `gd-engine` repo holding just the engine, renderer, and runtime, and a `gd-editor` repo holding the editor UI, which depends on and runs against `gd-engine` rather than the two being tangled together as they are today. This is the foundation the rest of the work plan sits on: a verifiable milestone (the engine builds and runs standalone; the editor is just a consumer of it), not just a conceptual split.

This split also opens a real question worth settling empirically rather than assuming: if `project.godot` turns out to be read only by the editor, and the editor itself moves toward .NET as part of this separation, patching Anvil into that specific file format may turn out to be unnecessary — superseded by the editor rebuild rather than a prerequisite for it. This gets revisited once the repos are actually split and the fibers within each to-do are examined.

**Three components, not two.** `gd-engine` and `gd-editor` depend on a third: `gd-build`, the shared build system (SCons scripts, platform/compiler detection, module registration) that both repos should pull in rather than each carrying its own copy of. Staying open to a fourth or fifth component turning up once the source is actually examined — the brief is to go in expecting three, not assume three is final.

**Where Mono/.NET fits — confirmed by reading `modules/mono` directly.** The three-way split holds, and `gd_mono.cpp` already draws the engine/editor line cleanly in its own code: the `TOOLS_ENABLED` branch uses `hostfxr_resolver` to find a system-installed .NET SDK (the editor has to locate and drive whatever `dotnet` the developer has), while the `!TOOLS_ENABLED` branch loads a bundled CoreCLR for shipped games with zero dependency on anything being installed. `modules/mono/editor/` is already its own isolated subtree — including a full `GodotTools` C# tooling suite: build invocation, `.csproj` editing, and `GodotTools.IdeMessaging`, a protocol Godot's editor already speaks to talk to external IDEs. `csharp_script.cpp`/`.h` is the one real offender: it sits outside that `editor/` subtree but hard-`#include`s `editor_node.h`, `inspector_dock.h`, and `signals_dock.h` directly — the same fix needed below applies here too.

Placement: `gd-engine` gets the CoreCLR/runtime-hosting path, the `glue/` interop layer, and `godotsharp_dirs.cpp` (a genuinely shared utility, not a leak — it has real, correct branches for both the editor and non-editor cases). `gd-editor` gets all of `modules/mono/editor/` as-is. `gd-build` gets `build_scripts/build_assemblies.py` and the `Directory.Build.props/.targets` plumbing that compiles the GodotSharp/GodotTools assemblies themselves.

One piece doesn't just relocate, it inverts: `GodotTools.IdeMessaging` exists today so Godot's editor (the hub) can notify an external IDE (a satellite). Once VS Code is the primary editing surface, those roles flip — VS Code becomes the hub, Godot's viewer/player becomes the thing being driven. The protocol's job is still needed; its primary/secondary direction needs rework, not removal. `GodotTools.OpenVisualStudio` has no equivalent flip — it's just dead weight once VS Code, not Visual Studio, is the target IDE.

**Finding the boundary — confirmed by grep.** Godot already compile-guards a large share of editor-only code behind `TOOLS_ENABLED`, plus the `editor/` directory tree, because it supports building export templates with no editor baked in. That existing guard is the rough draft of the `gd-engine` / `gd-editor` line, and the fork has 1164 `TOOLS_ENABLED` sites total — concentrated in `scene/` (137 files), `modules/` (81), `core/` (55), `platform/` (20), `servers/` (11), and only 2 in `editor/` itself. The boundary is smeared through engine-destined directories rather than cleanly isolated, as expected.

Most of those 1164 sites are harmless — they compile out cleanly with no cross-repo dependency. The real blocker signal is narrower: files with a hard `#include "editor/..."`, which can't compile without `editor/` physically present regardless of the macro. That's 11 files outside `main.cpp`: `scene/2d/skeleton_2d.cpp` pulls in three separate editor headers, `scene/gui/rich_text_label.h` leaks one from a header (infecting everything that includes it), plus `control.cpp`, `line_edit.cpp`, `shader.cpp`, `property_utils.cpp`, `occluder_instance_3d.cpp`, `animation_mixer.cpp`, two `skeleton_modification_2d*.cpp` files, and `core/extension/extension_api_dump.cpp`. `main.cpp` is its own category, not one of these to "fix" — it's supposed to bridge both, deciding whether to boot the editor or run a game, and likely belongs to `gd-editor` as the editor executable's entry point.

The fork already has a working fix for this, demonstrated in its own code: `core/extension/gdextension.h` hits the identical problem and solves it with a function-pointer hook (`EditorPluginRegisterFunc`) instead of an `#include` — core declares the slot, `editor/` registers the real implementation at runtime. `core/io/resource_importer.cpp` uses the same trick (`ResourceImporter::load_on_startup`). That's the template for fixing the 11 files above — apply the pattern already proven elsewhere in this exact codebase, not a rewrite.

- `gd-editor`: `editor/`, `modules/mono/editor/`, the ten `platform/*/export` and `platform/*/editor` subdirs pulled out of `gd-engine`'s copy, plus its own copies of `main/`, `misc/`, and `thirdparty/`.
- `gd-build`: `SConstruct` and the top-level build scripts (`methods.py`, `platform_methods.py`, `gles3_builders.py`, `glsl_builders.py`, `scu_builders.py`, `version.py`), `modules/mono/build_scripts/build_assemblies.py`, `modules/mono/Directory.Build.props`/`.targets`, and `misc/`.

**Full module-by-module boundary, done 2026-10-17 — supersedes "not reviewed individually yet."** Checked every module with `TOOLS_ENABLED` sites for its own `editor/` subfolder (the `modules/mono/editor/` pattern): 17 of 21 already have one (`gdscript`, `tilemap`, `gltf`, `vorbis`, `multiplayer`, `visual_shader`, `mp3`, `interactive_music`, `openxr`, `navigation_3d`, `gridmap`, `fbx`, `websocket`, `theora`, `objectdb_profiler`, `noise`, `navigation_2d`, `csg`). Checking the 17 "clean" modules for leaks *outside* their `editor/` subfolder (the way `mono`'s `csharp_script.cpp` leaked despite `mono/editor/` existing) found the real pattern: **every single one of the 17 leaks in exactly the same place**, `register_types.cpp`, which hard-`#include`s its own plugin header to call `EditorPlugins::add_by_type<SomeEditorPlugin>()` (e.g. `tilemap/register_types.cpp` pulling in `editor/tiles_editor_plugin.h`). This isn't 17 separate problems — it's one mechanical inconsistency, and `editor/register_editor_types.cpp` already proves the correct alternative: it registers the editor plugins for everything core/scene provides (every 2D/3D node editor, inspector plugin, etc. — dozens of them) entirely from the editor side, with zero leak back into `core/`/`scene/`. The fix for all 17 modules is relocating their plugin-registration block out of `register_types.cpp` and into `editor/register_editor_types.cpp`, matching a convention this codebase already uses everywhere else — not a redesign.

`gdscript` is the real outlier: its leaks extend well past `register_types.cpp` into `gdscript_tokenizer.cpp`, `gdscript_analyzer.cpp`, test files, and a complete embedded **Language Server Protocol implementation** at `modules/gdscript/language_server/` (`gdscript_language_server.cpp/h`, `gdscript_workspace.cpp`, `gdscript_text_document.cpp`, `gdscript_language_protocol.cpp`, `scene_cache.cpp`). That LSP server is real, working prior art directly relevant to the still-open "VS Code language support: TextMate grammar or full LSP server?" question below — worth reading before deciding Anvil Script's own approach, rather than designing one from scratch. Parked in `gd-engine` wholesale for now regardless, since it has to keep working until Anvil Script actually replaces it.

**`gd-engine` passes this criterion, confirmed 2026-10-17.** `scons target=template_debug platform=linuxbsd` produces `bin/godot.linuxbsd.template_debug.x86_64` cleanly, after two fixes beyond the symlink-to-copy swap above: the build needs `AUTHORS.md`, `DONORS.md`, `COPYRIGHT.txt`, and `LICENSE.txt` at the repo root (`core/SCsub` reads them to generate `authors.gen.h`/`donors.gen.h`/`license.gen.h` — project metadata, not engine/editor/build source, so it wasn't in the original manifest, but the build needs it present). **`gd-editor` also builds and runs, confirmed 2026-10-17** — after duplicating `gd-engine`'s `core/`, `scene/`, `servers/`, `drivers/`, `platform/`, `modules/` into it (see the `library_type` finding above for why this was the fallback). `scons target=editor platform=linuxbsd` produces `bin/godot.linuxbsd.editor.x86_64` cleanly, no errors, and it runs the same smoke-test project headless, exit `0`.

**Correcting the symbol-check method.** Both binaries report "no symbols" under `nm` — they're stripped, so `nm -C | grep EditorNode` returning zero on `gd-engine` was accidentally the right answer, not a real test (it would've returned zero on a stripped `gd-editor` binary too, which does contain `editor/`). The real check: `strings <binary> | grep "^EditorNode$"` — the literal class-registration string a `GDCLASS` macro embeds regardless of stripping. That returns `1` for `gd-editor` and `0` for `gd-engine`, which is the actual evidence the two builds differ as intended. (Binary sizes corroborate it too: 133M for `gd-editor` vs. 83M for `gd-engine`.)

## Viewer/player: the actual target, not a buildable `gd-editor`

**The `servers`/`drivers` de-duplication proof-of-concept, run to its conclusion 2026-10-17.** Picked up the leading candidate from the open questions (link `gd-editor` against `gd-engine`'s prebuilt archives instead of recompiling from source) and tried it on the two cleanest subsystems. Five iterations in, five distinct problems surfaced, each a different flavor of the same lesson — skipping an `SConscript` call skips more than that directory's compilation:

1. `EGL_ENABLED`/`GLAD_GLES2`/`GLAD_ENABLED` — a `CPPDEFINES` side effect of `drivers/gl_context/SCsub`, lost the moment that script isn't run, silently breaking an unrelated file in `platform/` that depends on it.
2. The generated `glad/gl.h` — a `CPPPATH` side effect of the same script.
3. `VK_USE_PLATFORM_XLIB_KHR` — same pattern, `drivers/vulkan/SCsub`.
4. `VK_USE_PLATFORM_WAYLAND_KHR` — same file, Wayland branch.
5. **The structural one:** pointing `CPPPATH` at `gd-engine`'s whole root while `gd-editor` still keeps local copies of `core/`/`scene/`/`platform/`/`modules/` means any header reachable through both paths (most of them, since `servers/`/`drivers/` headers reach back into `core/`) gets compiled as two distinct files per `#pragma once`'s path-based (not content-based) deduplication, and collides with itself — confirmed with `core/extension/gdextension_interface.gen.h` getting "redefined."

That fifth one is a ceiling, not a missing fix: cross-pointing `CPPPATH` at a whole sibling repo's root doesn't work while any local duplication overlaps it. The actual fix needs either a full one-pass de-duplication (no partial/incremental version) or a genuinely shared, single-source-of-truth headers location both repos reference — the "common space for the editor and modules to use" raised in conversation, not yet built. **Shelved, not abandoned** — and, per the finding below, not actually needed for the next milestone anyway.

**The pivot: `gd-editor` was the wrong target for the viewer/player.** Went looking at what the editor's own Play button does, expecting to find the thing a "viewer/player" needs to become. Found instead that it already exists: `editor/run/editor_run.cpp`'s `EditorRun::run()` doesn't launch a separate player binary. It builds a plain CLI argument list (`--path`, `--scene`, `--remote-debug <uri>`, `--editor-pid`, `--breakpoints`, `--debug-collisions`, etc.) and re-executes `OS::get_singleton()->get_executable_path()` — **its own binary** — as a child process via `create_instance()`. There is no editor/player binary split upstream at all; the same executable just behaves differently based on CLI args.

That means `gd-engine`'s binary — already built, already validated (headless scene run, exit `0`, confirmed 2026-10-17 above) — **is** the stripped-down viewer/player Point Z describes, as-is, with zero additional C++ work. Point it at a project with `--scene` instead of `--headless`, and it's doing exactly what the editor already spawns as a child process. The real remaining work is on VS Code's side: constructing that CLI invocation, and speaking the protocol below so the spawned instance can be observed and controlled. `gd-editor`'s own buildability drops off the critical path entirely — it only matters later if a transitional, full-featured Godot editor is wanted for whatever VS Code hasn't ported yet, which is a separate, deferrable concern from the viewer/player.

### The remote debugger protocol

**Why it exists.** The editor and the running game are separate OS processes (confirmed above — `create_instance()` spawns a child, it doesn't embed in-process). That separation is deliberate, for reasons that are architectural, not language-related: the game needs its own independent main loop; a crash in the game shouldn't take the editor down with it; and "run on device" means the game process is sometimes on a different physical machine entirely, which no in-process call of any kind can reach. The protocol is what keeps the editor "in the loop" with that separately-running instance once it starts — debugging, live scene inspection, profiling, and the embedded game view are all just clients of this one connection, not separate mechanisms.

**Transport.** TCP or a Unix domain socket, addressed by URI (`tcp://host:port`), opened via `RemoteDebuggerPeerTCP::create_tcp(uri)` / `create_unix(uri)` (`core/debugger/remote_debugger_peer.h`).

**Framing.** A 4-byte length prefix followed by exactly that many bytes of one `encode_variant`-encoded `Variant`, confirmed directly from `_write_out()`/`_read_in()` in `core/debugger/remote_debugger_peer.cpp`:
```cpp
encode_variant(var, nullptr, size);   // compute size first
encode_variant(var, buf + 4, size);   // then encode after the 4-byte header
out_left = size + 4;
```
Read side mirrors it: 4 bytes for the length, then that many bytes, then `decode_variant`.

**Envelope.** Always a 3-element `Array`, confirmed from `RemoteDebugger::_put_msg()` (`core/debugger/remote_debugger.cpp:104`):
```cpp
Array msg = { p_message, Thread::get_caller_id(), p_data };
```
`[message_name: String, thread_id: int, payload: Array]` — `payload`'s shape is message-specific, defined per-message by `serialize()`/`deserialize()` pairs in `debugger_marshalls.h` or built ad hoc.

**Dispatch.** `EngineDebugger::register_message_capture(StringName, Capture)` is a name → handler table, and the connection is fully symmetric — the game sends messages to whoever's listening, the listener sends messages back, same envelope, same wire, direction is just whoever calls `send_message` right now. In today's Godot that's the editor; in ours it needs to be VS Code.

**Encoding.** `core/io/marshalls.h`'s `encode_variant`/`decode_variant` — Godot's one general-purpose binary serialization format, the same one used for binary `.res`/`.scn` resource files and multiplayer RPC. Not debugger-specific; learned once, applies everywhere.

**Vocabulary**, pulled from every `send_message(...)` call site across the whole source tree:

| Namespace | Purpose |
| --- | --- |
| *(bare)* `debug_enter`, `debug_exit`, `stack_dump`, `stack_frame_var(s)`, `evaluation_return`, `output`, `set_pid` | Core script debugging — breakpoints, stack inspection, print/error output. Predates the namespaced convention below. |
| `scene:*` | Remote scene tree — live node inspection and manipulation of the *running* tree, not the one on disk |
| `performance:*`, `servers:*`, `visual:*` | Profiling and monitoring data, streamed continuously |
| `multiplayer:*` | Multiplayer-specific debug info |
| `snapshot:*` | Memory/object snapshot requests |
| `game_view:*` (`get_screenshot`, `window_size`, `hdr_state`, `open_scene`, `setup_complete`) | **Directly relevant** — almost certainly the exact protocol behind the embedded-game-view feature (`platform/macos/editor/embedded_game_view_plugin.h`), a working reference implementation of "remotely view and control a running game instance" close to word-for-word what VS Code's own viewer/player panel needs. Worth reading end-to-end before designing VS Code's side from scratch. |

**Why AnvilScript's native ABI doesn't make this protocol go away.** Raised and checked against AnvilScript's own design notes (`/home/badkraft/Projects/repos/anvil/notes/` — per its `README.md`, AnvilScript/ASL is design-only right now, no implementation; a prior v0.4.0-alpha predates the current architecture and has been removed). A native C++ ABI and .NET bindings address the *script-to-engine* boundary — how game logic calls into engine internals within one process, which is genuinely where `modules/mono`'s CoreCLR-hosting overhead lives. The debugger protocol addresses a different boundary entirely — the *process* boundary — and none of the three reasons that boundary exists (independent main loop, crash isolation, remote-device testing over a real network) are about scripting-language ABI at all. A perfect, zero-overhead Anvil Script running inside the game doesn't change any of them. The one legitimate adjacent idea: `libgodot`'s `GodotInstance` API (found earlier) could let VS Code embed the engine in-process instead of spawning it as a child, which would let the *local* case skip the socket — but that's a consequence of choosing in-process embedding via `libgodot`, unrelated to Anvil Script's ABI, and it wouldn't touch the remote-device case at all, which has no in-process option by definition. The protocol's vocabulary (the table above) likely survives either way, as the actual API surface — only the transport underneath it changes.

## Godot patch scope

Godot's scene content and its project settings live in different files, so they are separate targets for the Anvil swap.

Today scene content and project settings are two different formats serving two different purposes — Godot's own contributors have even discussed renaming them further apart (`.tscn`/`.tres` vs. the INI-style `project.godot`) rather than unifying them. Moving both onto Anvil removes that split: one format, one parser, for everything the engine reads and writes. That same unification is what gives the later scripting work a foundation to build on, rather than Anvil config and scene data sitting next to a scripting language that still speaks its own, unrelated syntax.

| File | Holds | Anvil role |
| --- | --- | --- |
| `.tscn` scene files | Each scene's node hierarchy, node types and properties | Replace with Anvil scene format |
| `project.godot` | Global project settings: autoloads, input maps, rendering, plugins | Replace with Anvil config |
| Other INI-style config (`export_presets.cfg`, editor settings) | Export and editor configuration | Replace with Anvil config |

The change is made inside the Godot source with the native C parser, patched in directly rather than registered as a ResourceFormatLoader/ResourceFormatSaver extension — Anvil is not a plugin riding on top of Godot's existing formats, it replaces the INI-style and scene readers/writers wholesale, using the existing C++ and .NET bindings. Godot's own loader/saver extensibility mechanism is otherwise left in place as good architecture; Anvil itself just isn't implemented as one of those extensions. Godot's own editor must still read back what is written, so the first milestone is a round trip: load an Anvil file, save it, and confirm the editor sees no difference.

## VS Code extension build-out

Every feature ships read-only first and becomes editable only after the read-only version is solid. This keeps the work clear of Godot's file-write expectations while the data shapes are still being learned.

1. **Scene tree dock:** the node hierarchy for the open scene, collapsible and expandable, read-only first.
2. **Inspector panel:** properties of the selected node, read-only first, grouped the way Godot groups them today.
3. **FileSystem dock:** the project's file and folder tree as Godot shows it today, including resource previews.
4. **Node and signal connections:** the dialog for wiring a node's signals to handler methods, and viewing existing connections.
5. **Animation track editor:** the keyframe timeline used to build animations — distinct from watching them play back, see the design note below.
6. **Import dock:** how an asset (texture, model, audio) is imported and its import settings.
7. **Output and debugger panel:** console output, the error/warning log, and debugger state.
8. **Project settings and editor settings:** editable screens for project-wide and editor-wide configuration.

Each of these ships read-only first and becomes editable only once the read-only version is solid, per the philosophy above.

**Milestone order changed, 2026-10-17 — supersedes "ships in list order" above.** The list above was written before `gd-engine` was proven working and the debugger protocol was characterized (see "Viewer/player" above). Re-sorting it through that lens: items 3, 4, 5 (building), 6, and 8 are file-based only, nothing changes for them. Items 1 (scene tree) and 2 (inspector) each have a file-based half already covered here *and* a live half this list didn't account for — the running tree/object state, reachable via `scene:*`. Item 7 (output and debugger panel) turns out to be **entirely** protocol-based, not file-based at all.

Two components this list never named, surfaced directly by this session's work, and both are prerequisites for item 7 and the live halves of 1/2:
- **A Play/Run orchestrator** — constructs the CLI invocation (`--path`, `--scene`, `--remote-debug <uri>`, `--breakpoints`, `--debug-collisions`, etc.), spawns `gd-engine`'s binary as a child process, manages its lifecycle. This is what makes "press Play in VS Code" real; nothing above covers it.
- **The protocol client itself** — a TypeScript implementation of the transport/framing/envelope/encoding/dispatch characterized above. Every live component (output/debugger panel now, live scene tree and inspector later, an embedded game view if wanted instead of a separate OS window) sits on top of this one library.

**Decision: build the Play orchestrator + protocol client + a minimal output/debugger panel first**, ahead of the file-based docks above, even though they're listed first. Reasoning: `gd-engine` already works and the protocol is already characterized, so this combination gets to a real, demonstrable, end-to-end loop — open a project, hit Play, see the scene run, see console output, hit a breakpoint — almost immediately. A read-only scene tree dock, while useful, doesn't exercise anything this session de-risked. The file-based docks (1, 3, 4, 5, 6, 8) remain the plan for everything after this first milestone, in whatever order opportunity favors.

**The Inspector became a real, editable right-side panel, and hit a real production bug along the way — 2026-10-18.** Followed through on "Godot editor parity" by moving the Inspector from a read-only `TreeView` under Explorer to its own `WebviewViewProvider` in a dedicated Activity Bar container (editable text fields, user can drag the view to the Secondary Side Bar for an actual right-panel layout, matching how Godot's own docks are user-repositioned too). Edits go through a surgical `TextEdit` via `document.positionAt()` on the exact source range of the value — not a whole-file reserialize — so a one-property edit stays a one-line diff. `GodotProperty`/new `GodotAttribute` (for header attributes like `name=`) now track exact source byte ranges for this.

Hit a real, reported bug doing this live against the user's actual project: editing the same property twice in a row corrupted it (`0.5→0.75` worked, `0.75→0.5` produced `0.55`, `0.5→0.25` produced `0.255` — compounding). Root cause: the Inspector kept reusing the same `SceneNode` object (and its now-stale byte offsets) across edits instead of re-parsing and re-locating after each one. Fixed by adding a stable `path` identity to `SceneNode` (`findNodeByPath()`) and reparsing immediately after every edit rather than mutating in place. `sequential-edit-test.js` reproduces the exact reported sequence and proves it's fixed. Also restored the user's real `main.tscn` (left at the bug's garbage value, `0.255`) back to `0.5`.

Node renaming followed, deliberately guarded: `canRename()` only allows it when nothing else in the file references the node by name yet (no children, no `[connection from=/to=]` entry) — a full cascading rename (updating child `parent=` paths and connection references automatically) is real, separate, unbuilt work, not something to silently half-implement given the file-corruption risk just dealt with.

**Milestone built and proven live, 2026-10-17.** New sibling repo `gd-vscode` — a real (if minimal) VS Code extension, not a prototype thrown away after. `src/protocol/variant.ts` is a hand-verified subset of Godot's binary Variant wire format (`core/io/marshalls.cpp`: 4-byte header with the `Variant::Type` tag in the low byte and a 64-bit flag at bit 16; strings are 4-byte length + UTF-8 + zero-pad to 4 bytes; arrays are 4-byte count + recursively-encoded elements), covering `NIL`/`BOOL`/`INT`/`FLOAT`/`STRING`/`ARRAY`/`PACKED_INT32_ARRAY`/`PACKED_STRING_ARRAY` — enough for the envelope and the `output` message, not a general codec yet. `src/protocol/peer.ts` implements the actual framing and envelope from `remote_debugger_peer.cpp`/`remote_debugger.cpp` as a TCP server (we're the listener; the game connects out to us, same as it connects out to the editor today). `src/playOrchestrator.ts` builds the same CLI args `editor_run.cpp` builds and spawns `gd-engine`'s binary.

Proved end-to-end against the real binary (`npm run test:protocol`, `src/test/live-debug-test.ts`) — not mocked: spawns `gd-engine` headless against a fixture project (`test/fixtures/smoke_project`, a GDScript script that prints a known string), and the test genuinely receives and correctly decodes real messages over the real protocol: `set_pid` (the game's actual PID), `output` (both the engine's own startup banner and the fixture's print), `error` (the full marshalled error struct, for a harmless "could not load global script cache" warning — expected for a project never opened by an editor's import pass), and `window:title`. Test asserts on the actual expected string and passes.

One real timing issue surfaced and is now commented in the fixture: `core/debugger/remote_debugger.cpp`'s `flush_output()` runs once per engine iteration (`poll_events()`); calling `get_tree().quit()` in the same frame as a `print()` can race ahead of that flush and the message never sends. The fixture now awaits a short timer before quitting — worth remembering for anything else built against this protocol that quits/stops quickly after producing output.

Godot stays open alongside for anything spatial or visual, such as positioning a 3D object or previewing a timer. The extension front end would use TypeScript and VS Code webviews over the same Anvil-backed files.

**Corrected 2026-10-18 — "Godot stays open alongside" doesn't mean the Godot editor.** It can't: Point Z has no Godot editor at all, only the stripped-down viewer/player, so spatial manipulation can't just "stay" in something that no longer exists. Checked the actual mechanism rather than leaving this as an unresolved tension: `scene/debugger/runtime_node_select.cpp` (1915 lines — real gizmo rendering, hit-testing, drag manipulation) lives in `scene/`, gated by `DEBUG_ENABLED` (`SConstruct:569`), not `TOOLS_ENABLED` — already compiled into `gd-engine`'s own binary, not editor-only. `editor/run/game_view_plugin.cpp` doesn't do the gizmo work itself; it's a thin remote controller sending `scene:runtime_node_select_*` messages over the same `send_message()` mechanism `gd-vseditor`'s `DebuggerPeer` already speaks. Confirmed the full round trip: drag a gizmo → `RuntimeNodeSelect` tracks state before/after → on release, sends `remote_undo_redo_action = [message, {object_id: {undo, redo}}]` (`runtime_node_select.cpp:1769-1789`) → the controller just applies the `redo` state, which for `gd-vseditor` is the already-proven `patchProperty` surgical edit, not new engineering. So: the *rendering and hit-testing* genuinely stays engine-side (only the real renderer has the real geometry/camera data), but "engine-side" now means "reachable by VS Code over the debugger protocol," not "locked inside a UI that disappears at Point Z." Full writeup in `gd-vseditor/doc/porting-plan.md`.

**Design note — preserve the familiar layout.** This taxonomy is not a license to design a new UI. Menu wording and organization may shift, but where things live — how a developer gets to signals, node configuration, properties, the scene tree — should stay recognizable to anyone who already knows Godot. Nobody should feel like they have to relearn an editor they already use.

The animation panel is the clearest example of where the line falls. Building an animation — the keyframe timeline and track editor — moves to VS Code like the rest of the inspector-style panels above. But *watching* an animation play, the preview player with its playback and scrubbing controls, stays Godot's job even at Point Z: pressing play in VS Code triggers whatever build is needed and hands off to the Godot viewer/player for the actual playback, rather than VS Code reimplementing a player of its own.

## Anvil DSL and scripting

Once Anvil script and its extensible DSL work in the native C parser, Anvil Script fully replaces GDScript as Godot's native scripting language. Until then, C# scripting stays and VS Code is simply set as its editor.

This is not a walled garden: Anvil already has .NET and Python bindings, with a Rust binding planned. Those bindings are the on-ramp for developers working in other languages, so someone writing Rust or Python can bridge into an Anvil-scripted Godot project through the bindings rather than being forced to hand-write Anvil Script directly. Anvil Script is the one native scripting language; the multi-language bindings are what keep that from locking other-language developers out.

There is also a reason to move now rather than later: Godot's own contributors have an open proposal to migrate GDScript itself off its current scripting-layer plumbing onto GDExtension, because that layer already causes subtle conflicts even for the two officially supported languages. Today's third-party language integrations (Python, Rust, JavaScript) are explicitly unofficial, advanced, build-it-yourself territory. Replacing GDScript outright with Anvil Script sidesteps that shaky shared layer rather than building a new language on top of it.

The VS Code language support level is undecided:

- **Syntax highlighting only:** a TextMate grammar, a few hours of work, but it is a hand-maintained definition that can drift from the real grammar.
- **Full LSP server over the parser:** diagnostics and hover come from the same parser Godot uses, so nothing drifts, at the cost of JSON-RPC, document sync and re-parsing on edits. It could sit on the existing Node binding rather than a new C binding layer.

The decision can wait until items 1 and 2 are done.

## Upstream tracking

When Godot adds node characteristics, node types, configuration settings, tools or widgets to its editor, this project needs to know, so the VS Code replacements get new features or enhancements and don't fall behind unnoticed.

The mechanism is not designed yet. Candidate inputs are each Godot release's notes and changelog, and a comparison of the node and property schemas the extension understands against what a new Godot version ships.
